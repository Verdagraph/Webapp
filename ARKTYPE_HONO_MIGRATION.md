# Fastify → Hono, then zod → arktype (staged)

> Migration plan for `arktype-hono` branch. Saved 2026-09-20 so it survives across sessions. Phase A is the active/current scope; Phases B and C are future work captured here for continuity.

## Context

The forms rewrite (superforms → in-house `createForm`) surfaced that zod was originally chosen only for `sveltekit-superforms` compatibility, and that a prior WIP attempt (`origin/migrate-arktype-hono`, Feb–Mar 2025) tried to migrate both the validation library (zod→arktype) _and_ the backend framework (Fastify→Hono) together, since Hono has first-class arktype support that Fastify doesn't. That branch stalled: Hono's OpenAPI tooling for arktype was too immature at the time (`hono-openapi`'s arktype resolver couldn't document request bodies, forcing a fragile split between two packages, with a `TODO: Change validator to hono-openapi validator once it supports Arktype better` left in the code and `generate-openapi.ts` never actually fixed for Hono).

That branch is ~18 months stale now and not mergeable (predates the current `packages/models` package structure entirely). This plan is a fresh attempt, informed by:

- A full inventory of the _current_ Fastify server (`apps/server`) and the _current_ full zod footprint across `packages/models`/`packages/ui`.
- Mining the old branch's Hono-side code for reusable patterns (DI, cookies, error handling) before it hit its OpenAPI wall.
- Fresh research confirming the Hono OpenAPI ecosystem has matured since then: `@hono/zod-openapi` (official honojs/middleware package) is now at 1.6.3, actively maintained, with a clean unified `OpenApiHono` + `createRoute()` + `app.openapi()` pattern; `hono-openapi` now ships its own validator (paired with `@hono/standard-validator`, since arktype implements Standard Schema) that appears to resolve the exact request-body-documentation gap that stalled the old branch.

Decisions made with the user:

- **Stage it, don't combine**: Fastify→Hono first (keeping zod, using the mature `@hono/zod-openapi`), _then_ zod→arktype once Hono is a proven, working baseline. Same "change one variable at a time" discipline as the forms rewrite's shallow-to-deep ordering — isolates whether a bug is the framework swap or the validator swap.
- **Full `packages/models` migration** to arktype (all ~22 files) when that phase happens, not just the users-domain schemas — most files are simple composition with no new constructs; the real complexity is concentrated in a few files, not spread evenly, so a partial migration wouldn't actually save much and would leave two validator libraries installed indefinitely.
- **Hand-rolled DI on plain Hono `Context`**, not the old branch's `hono-simple-di` dependency — and per-request DI turns out to be barely needed at all (see Phase A design below): only the authenticated `client` is genuinely per-request; `triplit`/`userRepo`/`emailSender` are just module-level singletons today under awilix too.

**Scope of the current branch's first push is Phase A only** (Fastify→Hono, zod kept). Phases B and C are captured here for continuity but are separate future work — pick this file back up before starting either.

## Current-state facts this plan depends on (from inventory)

- `apps/server` currently implements **only the `users` domain**, 8 routes, all under `POST /users/*`. Every other domain (gardens/workspaces/plants/cultivars/environments) has `packages/models` schemas + controller functions but no HTTP routes — `packages/ui` calls those directly against a live Triplit client. So the Hono migration's surface area is genuinely just these 8 routes plus the app-level plumbing.
- The **command layer is already framework-agnostic**: every function in `apps/server/src/users/commands/*.ts` has the shape `(command: XCommand, container: typeof diContainer) => Promise<...>`, no Fastify types imported. These port to Hono essentially unchanged — only `controllers.ts`, `plugins/*`, and `app.ts` are Fastify-coupled.
- **Real DI need is smaller than it looks**: awilix's "global singleton scope" (`triplit`, `emailSender`, `userRepo`) never varies per-request — only awilix's separate "request scope" (`client: UserAccount | null`, set by the auth `preHandler` hook) is genuinely per-request. So the Hono port needs _no DI framework at all_ for the singletons (plain module-level consts suffice) — only `client` needs `Context` (`c.set`/`c.get`).
- `apps/server`'s own npm `schema` script has a **pre-existing bug**: `cp openapi.json ../frontend/server.json` — `apps/frontend` doesn't exist (renamed to `apps/web` at some point without updating this line). The real consumer is `apps/web/server.json`, read locally (not via network) by `apps/web/orval.config.ts`. This has been silently broken — `apps/web/server.json` is stale, hand-placed from an old monorepo-refactor commit, not regenerated by any working pipeline today. **Fix as part of this phase** since the OpenAPI-generation script is being rewritten anyway.
- `apps/server/src/users/auth/tokens.ts` has a **pre-existing bug**: `decodeEmailConfirmationToken` verifies against `env.REFRESH_TOKEN_SECRET` instead of `env.EMAIL_CONFIRMATION_TOKEN_SECRET`. **Fix while porting this file** — same file being rewritten anyway, real bug, trivial fix.
- `common/emails/sender.ts` loads its handlebars templates via `fs.readFileSync(path.join(path.resolve(), email.path))` — i.e. relative to `process.cwd()`, fragile if the run/build layout changes. **Fix to `import.meta.url`-relative resolution** while porting this file.

## Phase A: Fastify → Hono, zod kept

### Package changes (`apps/server/package.json`)

Remove: `fastify`, `@fastify/awilix`, `@fastify/cookie`, `@fastify/cors`, `@fastify/swagger`, `@fastify/swagger-ui`, `fastify-type-provider-zod`, `fastify-cli`, `awilix`.
Add: `hono`, `@hono/node-server` (dev server), `@hono/zod-openapi` (route definition + validation + OpenAPI docs, one package), `@scalar/hono-api-reference` (docs UI — confirmed working in the old branch, nicer than Swagger UI, no reason to change).
Unchanged: `argon2`, `@triplit/client`, `handlebars`, `jsonwebtoken`, `nodemailer`, `zod` (stays for this phase).

### New module layout (`apps/server/src`)

```
app.ts                    — new Hono() + middleware wiring, same order as today: cors → auth (sets client) → error handler → router mount
env.ts                    — unchanged (zod), stays as-is this phase
container.ts              — NEW, replaces plugins/dependencies.ts: plain singleton consts (triplit, userRepo, emailSender), no DI framework
plugins/cors.ts            — hono/cors, same config (origin=CLIENT_BASE_URL, credentials, restricted methods/headers)
plugins/auth.ts            — simplified: JWT-decode + resolve user via userRepo (imported directly, not resolved from context) + c.set('client', user); requireAuth(c) helper reads c.get('client')
plugins/errors.ts          — app.onError((err, c) => ...) mapping ServerError subclasses + Hono's HTTPException to ServerErrorResponse; keep the same response shape as today
plugins/openapi.ts         — OpenApiHono doc registration (app.doc(...)) + Scalar docs UI mount
plugins/router.ts          — app.route('/users', userRouter)
common/errors.ts           — unchanged (already framework-agnostic)
common/emails/sender.ts    — port + fix the cwd-relative template path bug
common/emails/*.html        — unchanged
users/repository.ts        — unchanged (Triplit calls, no Fastify coupling)
users/auth/passwords.ts    — unchanged (argon2 wrappers)
users/auth/tokens.ts       — port; swap Fastify's reply.setCookie/request.cookies for hono/cookie's setSignedCookie/getSignedCookie; fix the REFRESH_TOKEN_SECRET/EMAIL_CONFIRMATION_TOKEN_SECRET bug
users/commands/*.ts        — port; only the `container` parameter's type changes (typeof diContainer → a plain ServerContainer type), call bodies unchanged
users/controllers.ts       — new: 8 routes via createRoute() + OpenApiHono.openapi(), calling the same commands/* functions
```

`container.ts` sketch (the DI simplification):

```ts
export type ServerContainer = {
	triplit: TriplitHttpClient;
	userRepo: UserRepository;
	emailSender: EmailSender;
};
const triplit = new TriplitHttpClient({
	serverUrl: env.TRIPLIT_URL,
	token: env.TRIPLIT_SERVER_TOKEN
});
export const container: ServerContainer = {
	triplit,
	userRepo: new UserRepository({ triplit }),
	emailSender: new EmailSender()
};
```

Controllers call `commands.login(body, container)` directly — no context resolution needed for these three. Only `client` goes through Hono's `Context` (`c.set('client', user)` in the auth middleware, `c.get('client')` in `controllers.ts`'s `update` route, the only one that calls `requireAuth`).

### Route porting pattern (`@hono/zod-openapi`)

Each of the 8 routes becomes a `createRoute({ method, path, operationId, description, tags: ['user'], request: { body: { content: { 'application/json': { schema: XCommandSchema } } } }, responses: { 200: { content: { 'application/json': { schema: z.string() } } }, description: '...' } })` + `app.openapi(route, async (c) => { const body = c.req.valid('json'); const result = await commands.x(body, container); return c.json(result); })`. This single call both validates the request body against the same `packages/models` zod schemas already used today and documents it in the generated OpenAPI spec — the exact combination `fastify-type-provider-zod` gave for free, now from an official Hono package instead.

Error-shaping: `@hono/zod-openapi`'s `OpenApiHono` constructor accepts a `defaultHook` for validation failures — wire it once at app construction to convert zod's issues into the same `ServerErrorResponse { message, details: { fieldErrors } }` shape `plugins/errors.ts` already produces for `ServerError` instances, so both paths (validation failure vs. thrown `ServerError`) return an identical response shape to what `apps/web`'s `createCommandHandler`/`AppErrors` convention already expects — no client-side changes needed.

**Improvement worth making while this hook is being rewritten anyway**: today's Fastify error handler joins AJV's `instancePath` with `.split('/').join('.')`, which for a nested array field would produce `field.0.sub` — inconsistent with the dot/bracket convention `packages/models/src/errors.ts` documents and that the client-side forms utility (`zodIssuesToFieldErrors`, built in the forms-rewrite session) already correctly implements as `field[0].sub`. This never surfaces today because every current server-side schema is flat (no arrays), but the new hook gets zod's own `issue.path` array directly (not a stringified AJV path), so it's free to reuse the exact same join logic as `zodIssuesToFieldErrors` — do that, so the convention is actually correct everywhere from the start rather than carrying the latent inconsistency forward.

**Intentionally NOT fixing**: `controllers.ts` has a literal typo in one route's URL — `url: 'requestEmailConfirmationOp'` (every other route's URL is a clean verb, no "Op" suffix — compare `'login'`, `'create'`, `'confirmEmail'`). This exact path (and the matching `operationId: 'UserRequestEmailConfirmationOp'`) is already baked into `apps/web`'s orval-generated client function names. Changing it would require regenerating and touching every caller — out of scope for a framework port whose goal is behavioral parity. Preserve it exactly, flagged here for a future cleanup pass.

### Migration order

1. `apps/server/package.json` deps swap; scaffold `app.ts`/`container.ts` skeleton (no routes yet) + `@hono/node-server`'s `serve()` entrypoint; confirm it boots.
2. Port `common/errors.ts` (unchanged), `common/emails/*` (fix cwd bug), `env.ts` (unchanged).
3. Port `plugins/cors.ts`, `container.ts`, `plugins/auth.ts` (simplified), `plugins/errors.ts`.
4. Port `users/repository.ts`, `users/auth/passwords.ts`, `users/auth/tokens.ts` (fix the secret-mixup bug, swap cookie API).
5. Port `users/commands/*.ts` (mechanical — container type only).
6. Build `plugins/openapi.ts` + write `users/controllers.ts`'s 8 `createRoute()`/`app.openapi()` definitions — last, since it composes everything above.
7. `plugins/router.ts` + final `app.ts` wiring; confirm full boot.
8. Rewrite `generate-openapi.ts` for Hono: today it does `buildApp()` → `app.inject({method:'GET', url:'/docs/json'})` → `writeFileSync` → `app.close()`, none of which exist on a Hono app. Replace with `buildApp()` → `await app.request('/doc')` (matching whatever path `app.doc('/doc', {...})` registers in `plugins/openapi.ts`) → `.json()` → `writeFileSync` (Hono has no `.close()` to call, and no artificial `setTimeout(...,500)` exit-delay hack should be needed since there's no open server/listener in this script to begin with — confirm and simplify). Also fix the `schema` npm script's copy destination (`cp openapi.json ../frontend/server.json` → `../web/server.json`).
9. Regenerate `apps/web/server.json` and run `apps/web`'s `codegen` script; diff the regenerated `src/lib/codegen/` against what's there today — request/response shapes aren't intentionally changing, so this should be a no-op or near-no-op; investigate and fix any unexpected drift rather than accepting it silently.

## Phase B: `packages/models` zod → arktype, all ~22 files (future)

- Convert each `commands.ts` file's zod schemas to arktype `type({...})`, preserving `.describe()`; `.refine()` → `.narrow()` for the two password-match cross-field checks.
- Special-case constructs found during inventory that need arktype-specific handling: `z.date()` (several files) → arktype `Date`; `observations/commands.ts`'s `z.set(z.string())`, `z.record(z.string(), z.any())` → arktype's Set/Record/`unknown` equivalents (verify exact syntax at implementation time — least-common constructs in the whole package, only appear here); the one inline `GeometryCreateCommandSchema.parse(...)` call inside `plants/generation/annual.ts` business logic → arktype's callable-validator equivalent.
- **Known pre-existing bug to flag (not silently fix) while touching this file**: `cultivars/commands.ts`'s `CultivarCollectionCreateCommand` has a `.refine()` whose predicate references `parentId` but whose message/path reference `userId` — looks like a real bug independent of the arktype migration; surface it, don't just carry it forward unexamined.
- `packages/models/src/utils.ts`'s `validateField(value, schema: ZodType)` → arktype `Type` equivalent (thin, ~1:1, but confirm arktype v2.2's actual call/result API before assuming `.safeParse()`-shaped semantics carry over).
- **Highest-effort file in this phase**: `packages/ui/src/state/form/zodIntrospection.ts` (built during the forms rewrite) reaches deep into zod's private `instanceof`/`._def` class hierarchy — arktype's AST is structurally different (public `.props`/introspection API, not a zod-style private class hierarchy), so this needs a redesign against arktype's actual model, not a mechanical port. `createForm.svelte.ts` (`schema.safeParse(data)`, `z.infer`, `z.ZodTypeAny` generic) and `formContext.ts` (`z.ZodTypeAny` type constraint) need the same generic-parameter swap.
- `zod` stays installed until Phase C also removes it from `apps/server`.

## Phase C: `apps/server` Hono+zod → Hono+arktype (future, last)

- Swap `@hono/zod-openapi` for the arktype equivalent. Current best candidate per research: `hono-openapi`'s own `validator`/`resolver`/`describeRoute` combo, paired with `@hono/standard-validator` (arktype implements Standard Schema) — **this exact current API needs a throwaway one-route spike at the start of this phase** before committing across all 8 routes, since documentation research during planning gave partial/summarized answers, not a verified end-to-end example. This is exactly the piece that stalled the old branch, so don't assume it's solved without proving it first.
- Swap `env.ts` to arktype, mirroring the old branch's simple, already-proven pattern (`EnvSchema(process.env)`, `instanceof ArkErrors` check, no framework glue needed since it's a one-shot startup validation, not request-lifecycle).
- Remove `zod` from `apps/server/package.json`, then from `packages/models`/`packages/ui` package.json files (final cleanup, mirroring how the forms-rewrite PR ended with dependency removal).
